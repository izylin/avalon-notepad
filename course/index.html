How Avalon Notepad Works
01

Meet Avalon Notepad

A scorekeeper's clipboard for a game that has none — and what happens the instant you tap a seat.

The problem it solves

The Resistance: Avalon is a social deduction board game played entirely face-to-face, around a table, with no screens involved — until someone needs to remember who voted what three rounds ago. That's the gap Avalon Notepad fills.

🪑
Live at the table

One player runs it on their phone while everyone else plays with physical cards — it never controls the game, only records it.

🧠
A memory aid, not a rulebook enforcer

It tracks teams, votes, and quest results so players can review "wait, who proposed round 2?" without relying on memory.

🔒
Never leaves your phone

All game data is saved only in your browser's local storage — nothing is uploaded, unless you explicitly send feedback.

The App Brain never edits, it replaces

Here's the function seat 4's tap actually calls. It lives in src/app/page.tsx:

CODE 
function toggleTeamSeat(seat: number) {
  updateState((cur) => {
    const exists = cur.pickedTeam.includes(seat);
    if (!exists && cur.pickedTeam.length >= cur.missionSizes[cur.currentMission]) return cur;
    return { ...cur, pickedTeam: exists ? cur.pickedTeam.filter((s) => s !== seat) : [...cur.pickedTeam, seat].sort((a, b) => a - b) };
  });
}
PLAIN ENGLISH

Define what happens when a seat is tapped during team-picking.

Hand the current game state to a helper, and describe how to change it.

Check: is this seat already on the team?

If not, and the team is already full, do nothing — refuse the tap.

Otherwise, build a whole new copy of the game state: either seat 4 removed from the team, or added and the list re-sorted.

Notice what's missing. That's the trick — this function's only job is describing the new state. Saving it is somebody else's problem.

💡
The flipbook principle

Instead of erasing and redrawing on the same page, this app draws a brand new page for every change and flips to it — the old page is thrown away. Engineers call this immutability. It sounds wasteful, but it's exactly what makes it safe to hand this game state to a saving function, a history log, and a screen redraw all at once — nobody can step on anybody else's toes, because nobody is allowed to erase anything.

Who actually does the saving

Every one of those "brand new pages" passes through one more function before it's safe: persistState, also in page.tsx.

CODE 
function persistState(nextState: GameState) {
  try {
    const serialized = JSON.stringify({ ...nextState, updatedAt: Date.now() });
    if (serialized.length > 256 * 1024) return false;
    localStorage.setItem(storageKey, serialized);
    return true;
  } catch {
    return false;
  }
}
PLAIN ENGLISH

Take whatever the new game state looks like.

Turn it into JSON — plain text — and stamp it with the current time.

Refuse to save if it's grown past 256KB, so one runaway game can't quietly fill up your browser's storage.

Write that text into localStorage, under a fixed key name.

Report back whether the save actually worked, so the caller can warn you if it didn't.

This is why closing the app mid-game and reopening it puts you right back where you left off — every single tap, not just "end of round," gets written to disk.

Meet the Cast

Nine files, each with exactly one job. Know who does what, and you'll know exactly where to point an AI coding tool.

An orchestra, not a solo act

Think of this codebase like an orchestra. game.tsis the sheet music — the rules every player must follow, written down once and never broken. page.tsx is the conductor, holding the current state like a baton and cueing every section. Everything else is an instrument section: it plays its part and nothing more.

🎻
Why this matters for steering AI

When you ask an AI tool to "add a rule that a rejected vote skips the leader," you want it editing the sheet music (game.ts), not improvising inside a random instrument's part. Knowing the cast means you can say exactly that.

03

How the Pieces Talk

Nobody moves on their own. Understand this rule and "it's not showing up" bugs stop being mysterious.

The puppeteer's strings

Picture page.tsxas a puppeteer, and SeatSvg as a puppet on stage. The puppeteer decides everything the puppet shows — which seat is the leader, who's on the team, who voted what — by pulling strings down onto it. Those strings are called props.

The puppet can't reach up and move its own strings. If it wants something to change — say, a tap on seat 4 — it can only tug back on one string the puppeteer left dangling for exactly that purpose: a callback.

↓
Props flow down

page.tsx passes leaderSeat, teamSeats, voteMap, and identityTags into SeatSvg as plain data.

↑
Callbacks flow up

SeatSvg never edits that data. It only calls onSeatClick(seat) — a function page.tsx handed it — and waits.

🔁
page.tsx decides, then redraws

page.tsx runs the real logic, produces a new state, and passes fresh props back down. The puppet redraws itself to match.

The callback in the wild

During the voting phase, every seat tap is wired to this function in page.tsx in page.tsx:

CODE 
function toggleVoteSeat(seat: number) {
  updateState((cur) => {
    const votes = { ...cur.votes };
    votes[seat] = votes[seat] === "agree" ? "reject" : "agree";
    return { ...cur, votes };
  });
}
PLAIN ENGLISH

When seat N is tapped during voting...

...start a state update, copying the current votes so far.

Flip that seat's vote: agree becomes reject, reject (or unset) becomes agree.

Hand back the new state with the updated votes.

SeatSvg itself has zero knowledge of what "agree" or "reject" even means — it just renders whatever voteMap prop it was given, and reports taps through onSeatClick. Every seat's color, checkmark, and label is a direct reflection of state living up in page.tsx.

Unidirectional data flow

Notice SeatSvg never talks back to game.ts, and game.ts never reaches into SeatSvg. Data only ever flows in one loop: down as props, up as callbacks. This discipline is what makes a UI predictable — when something on screen is wrong, you always know to start at the top and work down, never guess randomly.

04

Leaving the Browser

Almost everything in this app never leaves your phone. Here's the one path that does — and the bouncer guarding its door.

Two very different kinds of "saving"

You already met one destination in Module 1: localStorage, which never leaves the device. There's exactly one other destination in this entire app, and it's much bigger: submitting feedback through the 📮 button in the corner.

💾

localStorage

Every game state, saved constantly, stays on this one device forever. No network request involved — it's closer to a notepad than a mailbox.

📮

Feedback submission

A real POST request to a server, which creates a GitHub Issue. This is the app's only outbound door.

The bouncer at the door

Anything that leaves the browser needs a checkpoint. That checkpoint lives in src/app/api/feedback/route.ts — the app's one API route. Think of it like a nightclub bouncer checking wristbands: no more than 3 submissions per visitor per minute.

CODE 
function rateLimited(key: string) {
  const now = Date.now();
  const recent = (hits.get(key) ?? []).filter((t) => now - t < RATE_LIMIT.windowMs);
  if (recent.length >= RATE_LIMIT.max) {
    hits.set(key, recent);
    return true;
  }
  recent.push(now);
  hits.set(key, recent);
  return false;
}
PLAIN ENGLISH

For this visitor's identifying key, check: how many submissions came in during the last 60 seconds?

Throw out anything older than a minute — only recent wristband scans count.

If they've already hit 3 in the window, turn them away (this is rate limiting).

Otherwise, stamp this new visit with the current time and let them through.

This runs before a single byte of your screenshot or message is even looked at — it's the cheapest possible check, done first.

Why the GitHub token never touches the browser

The API route reads a GitHub access token from an environment variable — never sends it to the page. Anything shipped to the browser is visible to anyone who opens developer tools, so a real secret can only ever live on the server. If it's missing, githubConfig() returns null and feedback fails safely with "not configured," rather than half-working.

05

The Clever Tricks

Two patterns worth stealing for your own projects, plus how to think like a debugger when something breaks.

Never trust the suitcase without scanning it

localStorage is just a text file sitting in your browser. Anyone with dev tools open could hand-edit it into garbage — or a future version of the app could save a shape this version doesn't expect. Before the app ever loads a saved game, it runs it through a security checkpoint: isSavedGameState, like a scanner checking every bag before it's allowed onto the plane.

CODE 
function isVotes(value: unknown, playerCount: number): value is Record<number, Vote> {
  if (!isRecord(value) || Object.keys(value).length > playerCount) return false;
  return Object.entries(value).every(([seat, vote]) => (
    isSeat(Number(seat), playerCount) && (vote === "agree" || vote === "reject")
  ));
}
PLAIN ENGLISH

Given some unknown value pulled out of storage, decide whether it's actually a valid votes record.

Reject it outright if it isn't even an object, or has more entries than there are players.

Otherwise, check every single entry...

...the seat number must be real, and the vote must be exactly "agree" or "reject" — nothing else sneaks through.

This function is one of dozens of tiny checks inside isSavedGameState. If even one field fails its scan, the entire save is thrown out and treated as if it never existed — better an honest "please start a new game" than a screen half-built from corrupted data.

⚠️
Why this matters for you

Any time your app loads data from somewhere you don't fully control — local storage, a URL, a file upload, another website's API — assume it could be wrong, tampered with, or from an old version of your own app. Ask an AI tool to "validate this before trusting it," not just "load this."

A detective's case board, not a single sticky note

The Identity Tags panel doesn't just remember "seat 4 is tagged Merlin." It remembers when you decided that — because your suspicions change as the game unfolds, and reviewing Quest 2 should show what you believed back then, not what you believe now.

Every tag you place is logged as an event with a start point, and — once you retag that seat — an end point. It's a corkboard where old notes stay pinned with their dates instead of being erased.

CODE 
export function effectiveIdentityTags(state: GameState, missionIndex: number): Record<number, IdentityTag> {
  return (state.identityTagEvents ?? []).reduce<Record<number, IdentityTag>>((tags, event) => {
    if (event.startMission <= missionIndex && (event.endMission === undefined || missionIndex < event.endMission)) {
      tags[event.seat] = event.tag;
    }
    return tags;
  }, {});
}
PLAIN ENGLISH

Given the whole game and "which quest am I looking at right now"...

...walk through every tag ever placed, building up the answer one note at a time.

Only count a note if it started by this quest, and (if it was later removed) hadn't been removed yet at this quest.

If it counts, this seat shows that tag for this snapshot in time.

Move to the next note.

Hand back the finished snapshot: exactly what the board looked like at that quest.

🕰️
Log events, don't overwrite state

This is a general pattern: instead of storing "the current value" and losing history every time it changes, store a list of dated events and compute "the value as of any point in time" on demand. It costs a little more code up front and buys you a rewindable history for free.
